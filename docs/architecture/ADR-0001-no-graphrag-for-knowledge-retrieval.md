# ADR-0001 — Use hybrid retrieval over pgvector, not GraphRAG

**Status:** Accepted · **Date:** 2026-09-12

## Context

The AI Assistant answers customer and investigator questions from the knowledge base
(`docs/knowledge-base/**`) and finds investigators matching a customer's requirements.
The question was raised whether to adopt GraphRAG — LLM-driven extraction of entities and
relationships from the corpus, community detection over the resulting graph, and
pre-generated community summaries used to answer queries.

GraphRAG's distinctive capability is **global sensemaking**: answering questions whose
answer exists in no single chunk ("what are the recurring themes across this corpus?").
That capability is real and vector retrieval cannot reproduce it.

The decision turns on whether this product has that problem, and on whether GraphRAG's
retrieval model is compatible with our authorization model.

## Decision

**Do not adopt GraphRAG.** Retrieval stays hybrid search over PostgreSQL:

- pgvector for semantic similarity
- `tsvector` / BM25 for lexical match
- the two fused by reciprocal rank fusion
- frontmatter (`audience`, `locale`, `tags`, `visibility`) as pre-filters
- curated `related` / `supersedes` links followed at retrieval time for one-hop expansion
- optional cross-encoder reranking over the fused top-N

Investigator discovery is **not retrieval at all**: it is SQL and PostGIS behind a
structured tool, per `investigator-discovery`.

## Reasons

### 1. The permission model is structurally incompatible — decisive

Our retrieval security model requires that every retrievable unit map 1:1 to an
authorizable row:

```
vector search → row IDs → load from PostgreSQL → authorize → survivors reach the prompt
```

GraphRAG's global search answers from **community summaries**: text pre-generated by
blending many source documents together. A summary spanning a `staff`-visibility document
and an `authenticated` one has the disclosure baked into generated text. There is no row
to authorize and no way to filter it after the fact.

Making it safe would require a separate graph per visibility scope, and regenerating every
summary that touched a document whose visibility later narrowed. That contradicts
`plan.md` §17 and the `permission-aware-rag` skill.

This platform holds private evidence about real people. A retrieval architecture whose
units cannot be authorized is not an acceptable tradeoff here.

### 2. There is no global-sensemaking query

Every question the Assistant handles is local and factual — "how long is a quote valid",
"can I cancel after paying", "who works near Yerevan". The answer lives in one chunk, or
in one SQL result. No user asks for emergent themes across the FAQ.

### 3. We author the corpus, so the structure is already known

The knowledge base is a curated set we write, on the order of hundreds of documents across
three locales — not an unstructured corpus of unknown shape. GraphRAG would spend LLM
calls probabilistically re-deriving structure we already recorded deterministically in
frontmatter (`tags`, `related_code`, `audience`, `supersedes`). That is strictly worse than
reading what we wrote.

### 4. Indexing cost fights the documentation-first rule

Documentation changes in every task that changes behaviour. GraphRAG re-indexing means
LLM extraction plus community re-summarization on that cadence. LazyGraphRAG reduces this
materially, so cost alone would not decide it — but it does not address reason 1.

## Alternatives considered

| Alternative | Why not |
|---|---|
| **GraphRAG (full)** | Reasons 1–4 above. Reason 1 alone is disqualifying. |
| **LazyGraphRAG** | Fixes the cost objection, not the permission objection. |
| **Vector-only (status quo)** | Viable, but misses exact terms — status names, "Stripe Connect", "chain of custody". Hybrid is a cheap, strict improvement. |
| **Dedicated graph database** | New store, new sync path, second source of truth. `plan.md` §25 explicitly defers this until metrics justify it. |
| **Embedding investigator profiles** | Rejected in `investigator-discovery`: approximate answers to exact questions, stale on every availability change, and an unverified investigator could surface on profile-text similarity. |

## Consequences

**Accepted:**
- No global-sensemaking capability. If a product need for one appears, this ADR is revisited.
- Relationship traversal is limited to curated one-hop links, not inferred multi-hop paths.

**Gained:**
- Every retrieved unit is an authorizable row; the permission model holds end to end.
- One store. No separate index to keep synchronized with PostgreSQL.
- Retrieval quality improves through hybrid search and reranking, both of which are cheap
  and reversible.
- Indexing stays proportional to edits, which keeps the documentation-first rule affordable.

## The narrow case where a graph would be right

Not the knowledge base: **within a single investigation** — entities, relationships,
contradictions, timelines. "What connects A to B?" is genuine multi-hop that SQL does
poorly and vectors cannot do.

If that is ever built, it must be **per-case, small, and curated by the human
investigator**, not LLM-extracted. An investigator asserting that two entities are the same
person, with evidence, is the entity-resolution discipline in `evidence-integrity`. An
LLM-inferred edge in an investigation report is exactly the fabrication that the
FACT / CLAIM / INFERENCE classification exists to prevent, and it could reach a court.

That is a curated knowledge graph, not GraphRAG. It is a separate decision and a separate ADR.

## Revisit this when

- A product requirement appears for corpus-wide synthesis ("summarize the themes in this
  quarter's disputes") that hybrid retrieval demonstrably cannot serve.
- The knowledge base grows past roughly 10,000 documents **and** measured retrieval quality
  degrades despite hybrid search and reranking.
- A permission-preserving graph retrieval method emerges — one whose retrievable units map
  1:1 to authorizable rows. That would remove reason 1, the decisive one.
- Case-level investigation tooling is built, at which point the curated case-graph above is
  evaluated on its own terms.
